# Installation contract

Purpose: install slopmemr hooks and a runtime that survives removal of the development checkout.
Authority: behavioral contract for src/installation; native hosts retain control of hook trust and authentication.
Expected use: consult before modifying setup/update/uninstall or their tests.
Lifecycle: update with installation format, launcher, native host or recovery changes.

The ordinary package includes Node: unpack the archive and run `./bin/slopmemr install codex` (or `claude`). It registers hooks and four direct MCP tools and publishes `~/.local/bin/slopmemr`. No separate Node installation is required. `slopmemr update codex --target /absolute/package-directory` consumes an explicitly downloaded package; it does not fetch a release. `pnpm package` builds the current platform archive and checksum under `dist/releases`. Publication remains separate.

`pnpm dev-install -- --runtime codex` builds a standalone Node 24 ESM bundle, runs setup and exposes `~/.local/bin/slopmemr`. For Claude use `--runtime claude`; its native profile supplies the existing Claude subscription for Haiku. Codex uses its own ChatGPT profile for Luna. CLI profile overrides must match the selected runtime. The parent development folder remains named slopmem.

Setup selects a native profile, preserves unrelated hook settings, and installs handlers for SessionStart, UserPromptSubmit, PostToolUse, Stop and SubagentStop. Codex owns enabling its hooks feature through `codex features enable hooks`. The user reviews trust in the native host when required. Setup does not login, request a key, start inference or start the resident. Claude defaults to `CLAUDE_CONFIG_DIR` or `~/.claude`; its launcher embeds `--claude-home`. Old Claude installations are rebound on update without borrowing their former Codex login. The first observation starts the resident automatically.

The installed hook command always points to `/bin/sh` and a stable profile-local `.slopmemr/<runtime>/hook-launcher.sh`. The launcher points to an immutable bundle under the selected data directory's `runtime/<sha256>/slopmemr.mjs`. Codex and Claude registrations can coexist in one profile directory. The dedicated `slopmemr-hook.mjs` bundle includes only intake, transport and startup code. It does not import resident, storage, compactor or MCP implementations. A separate resident launch descriptor starts the full application. Each snapshot retains its own executable Node and license. The full application bundle includes Effect, the Node adapter and UNII; build rejects external non-Node dependencies. Their license notices accompany every immutable snapshot. Runtime paths are shell-quoted, including apostrophes.

The shared public command has its own destination-local `.slopmemr` lock, ownership and recovery journal, so choosing a different memory directory cannot create a second publisher for the same command. Public-command conflicts are checked before changing native registration.

A SQLite BEGIN IMMEDIATE transaction owns each profile installation until completion. Never unlink the lock database: contenders must open the same inode. Atomic file writes use private exclusive temporary files, fsync the file, rename, and fsync the directory. Journals contain expected ownership and runtime references, never complete native settings or credentials.

Install order is journal → launcher → native handlers → ownership → journal removal. Uninstall order is journal → handler removal → launcher removal → ownership removal → journal removal. A failed operation leaves a journal. Repeating the same operation reconciles the current configuration, preserving unrelated edits made after the interruption. Changing operation while recovery is pending fails. Recovery accepts only the journal's old/new launcher digests and exact owned handlers; changed or duplicate handlers require reconciliation.

Object key order does not determine ownership. Array order does. Repeated setup/update preserves the existing handler position. Missing handlers are permitted during recovery and uninstall; a normal update treats them as a conflict. Optimistic reread detects native configuration changes before publication, but external editors do not share the installation lock, so this is not a filesystem compare-and-swap.

`slopmemr doctor codex|claude` reads registration, launcher and snapshot state. It does not create directories, acquire a lock, launch the resident or probe authentication. `slopmemr uninstall ...` removes owned registration and its profile launcher, retaining project memory and immutable runtime snapshots. Codex's enabled hooks feature and the shared public command remain available for other registrations.

Update selects a shared durable runtime target, gracefully drains an existing resident, waits for lifetime ownership release, and starts and verifies the selected build. Initial installation leaves startup to the first hook. `slopmemr repair` restores missing owned hooks/MCP bindings or resumes a journal and rejects externally modified bindings. `slopmemr restart` gracefully restarts the selected build. `slopmemr stop` drains accepted operations. Ping identifies application, protocol, version and implementation digest, and clients validate responses against the requested operation.

Offline installed-artifact validation is `pnpm test:installed`. Explicit live native-agent validation is `pnpm test:native`; it uses a synthetic project, a temporary native profile referencing Codex's existing ChatGPT login, and Luna. The live witness never decodes or copies credentials and retains source-free evidence in docs/validation/native-agent.json.


SessionStart emits a tiny guide to `slopmemr_snapshot`, `slopmemr_zoom`, `slopmemr_status` and `slopmemr_roots`, with CLI fallback. It does not inject a memory snapshot. MCP is a stdio proxy to the same resident; client EOF drains admitted responses and leaves the resident alive. Claude configuration uses `~/.claude.json` by default or the explicitly selected profile's `.claude.json`; Codex uses its profile's `config.toml`. Foreign entries are preserved and a foreign `slopmemr` entry is a conflict.

Snapshot reads return the available contiguous prefix immediately, including when newer records await compaction. Coverage, ingestion timestamps and processing state accompany the text. An empty pool returns empty text. Zoom uses aligned power-of-two record ranges: a parent returns two independently ready child slots; a leaf returns a zero-based UTF-8 page of the original record.

Legacy installations with a single combined hook/resident bundle require one explicit `slopmemr update codex|claude --profile /absolute/profile` per installed native profile. Doctor reports the missing dedicated hook/MCP capability. Old executables predating shared selection cannot honor that selection until their launchers are migrated; custom legacy profiles are not automatically enumerated. After migration, older hook launchers resolve the shared selected resident build.

Automatic activation uses a conditional shutdown containing the observed PID and full runtime identity, checked by the receiving resident. A legacy resident lacking this capability must be stopped explicitly with `slopmemr stop` before repeating update. Unknown endpoints are rejected; merely matching the memory directory or CLI digest is insufficient. A known immutable snapshot can be reconciled only after checking its canonical installation location, manifest and CLI/hook/Node hashes. Restart and update share one scoped activation lock.

A separate profile delivery journal records setup/update intent and the public-command destination before native changes. It survives profile and public-command publication and is removed only after shared selection and activation succeed. Repair resumes this recorded delivery; ordinary repair without such a journal only restores that profile and cannot select an older runtime globally. Uninstall requires pending delivery recovery first. The public launcher retains both custom data and public-command directories for recovery.

Doctor reports hook registration, MCP registration and runtime availability independently. An MCP conflict does not hide healthy hooks or runtime artifacts. Pending installation/delivery journals remain visible as recovery-required even before ownership is first published.
